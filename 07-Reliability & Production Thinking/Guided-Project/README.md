# RAG with n8n — Knowledge Pipeline & AI Agent

## 1. نبذة عن المشروع (Project Overview)

يهدف هذا المشروع إلى بناء نظام **Retrieval-Augmented Generation (RAG)** باستخدام **n8n** و**Supabase Vector Store**، لفهم كيفية تجهيز مصادر المعرفة وتخزينها واسترجاع المعلومات منها عند الإجابة عن أسئلة المستخدمين.

يركّز المشروع على بناء نظام RAG من مكوناته الأساسية بدلًا من الاعتماد على منصة جاهزة تخفي تفاصيل التنفيذ. يبدأ العمل بتحويل المستندات إلى أجزاء نصية، وإنشاء **Embeddings** لها، وتخزينها في قاعدة بيانات متجهية، ثم ربط قاعدة المعرفة بـ **AI Agent** يستطيع البحث فيها واستخدام النتائج لصياغة إجابات مرتبطة بالمصادر.

يتكوّن المشروع من جزأين رئيسيين:

- **Knowledge Ingestion Pipeline:** تجهيز المستندات ومعالجتها وتخزينها في قاعدة المعرفة.
- **RAG AI Agent:** استقبال أسئلة المستخدمين واسترجاع المعلومات ذات الصلة واستخدامها لتوليد الإجابات.

## 2. أهداف المشروع (Project Objectives)

يهدف المشروع إلى:

- فهم البنية الأساسية لأنظمة **RAG** وآلية عملها.
- بناء **Workflow** لمعالجة المستندات باستخدام n8n.
- استخراج النصوص من ملفات PDF وتحويلها إلى أجزاء قابلة للبحث.
- إنشاء **Embeddings** للنصوص باستخدام نموذج مخصص لذلك.
- تخزين المستندات وتمثيلاتها الرقمية في **Supabase Vector Store**.
- تنفيذ **Semantic Search** لاسترجاع المعلومات المرتبطة بأسئلة المستخدمين.
- ربط قاعدة المعرفة بـ **AI Agent** باعتبارها أداة للبحث.
- فهم الفرق بين **Knowledge Base** و**Memory**، وبين **Retrieval** و**Generation**.
- اختبار جودة الاسترجاع ومدى اعتماد الإجابات على المعلومات المتاحة.

## 4. بنية النظام (System Architecture)

يتكون النظام من مسارين مترابطين:

### أولًا: Knowledge Ingestion Pipeline

مسؤول عن تجهيز المعرفة وتخزينها قبل استخدامها في الإجابة عن الأسئلة.

```text
Google Drive Trigger
        ↓
Edit Fields
        ↓
Google Drive Download
        ↓
Extract From File
        ↓
Default Data Loader
        ↓
Recursive Character Text Splitter
        ↓
OpenAI Embeddings
        ↓
Supabase Vector Store
```

### ثانيًا: RAG AI Agent

مسؤول عن استقبال سؤال المستخدم، والبحث عن المعلومات ذات الصلة، ثم صياغة الإجابة.

```text
Chat Trigger
      ↓
   AI Agent
   /   |    \
Gemini Memory Vector Store Tool
               ↓
       OpenAI Embeddings
               ↓
        Supabase Vector Store
               ↓
        Relevant Documents
               ↓
            AI Agent
               ↓
             Answer
```

## 5. تجهيز قاعدة المعرفة (Knowledge Ingestion Pipeline)

تبدأ عملية تجهيز المعرفة من ملفات موجودة في Google Drive، ثم تمر بعدة مراحل لتحويلها إلى معلومات قابلة للبحث.

### 5.1 استقبال الملفات وتنزيلها

يُستخدم `Google Drive Trigger` لمراقبة المجلد المحدد وتشغيل الـ Workflow عند حدوث التغيير الذي تم ضبطه.

بعد ذلك، تُستخدم `Edit Fields` لتنظيم بيانات الملف واستخراج `file_id`، ثم تُستخدم `Google Drive Download` لتنزيل محتوى الملف.

يساعد الاحتفاظ بمعرّف الملف ومعلوماته في ربط الأجزاء النصية بمصدرها الأصلي من خلال **Metadata**.

### 5.2 استخراج النص (Text Extraction)

تُستخدم `Extract From File` لاستخراج النص من ملفات PDF وتحويل المحتوى إلى نص يمكن معالجته في المراحل التالية.

لا يمكن استخدام بيانات الملف الوصفية وحدها بديلًا عن محتواه؛ لذلك تمثل عملية استخراج النص خطوة أساسية قبل إنشاء الـ Embeddings.

### 5.3 تقسيم النص (Chunking)

تُستخدم `Default Data Loader` لتحويل المحتوى إلى صيغة Document، مع إمكانية إرفاق معلومات المصدر ضمن `Metadata`.

ثم يُستخدم `Recursive Character Text Splitter` لتقسيم المستند إلى أجزاء أصغر تسمى **Chunks**.

يساعد التقسيم على استرجاع الأجزاء الأكثر ارتباطًا بالسؤال بدلًا من استرجاع المستند كاملًا.

يتأثر اختيار `Chunk Size` و`Chunk Overlap` بطبيعة المحتوى وطول الفقرات والأسئلة المتوقعة. لذلك تُعد القيم المستخدمة نقطة بداية للتجربة والتحسين، وليست إعدادات مثالية لجميع المستندات.

### 5.4 إنشاء Embeddings

تُستخدم `OpenAI Embeddings` مع نموذج `text-embedding-3-small` لتحويل كل Chunk إلى تمثيل رقمي يسمى **Vector**.

تتيح هذه التمثيلات إجراء مقارنات دلالية بين النصوص، بحيث يمكن استرجاع محتوى ذي معنى مرتبط بالسؤال حتى عندما تختلف الكلمات المستخدمة.

يجب أن تكون أبعاد الـ Embeddings متوافقة مع تعريف عمود `embedding` في قاعدة البيانات، وأن يُستخدم نموذج متوافق عند تخزين المستندات وعند تنفيذ البحث.

### 5.5 تخزين المعرفة (Vector Storage)

تُستخدم `Supabase Vector Store` لتخزين الـ Chunks والـ Embeddings ومعلومات المصدر.

يعتمد التصميم على **Supabase** مع **PostgreSQL** وامتداد `pgvector`.

عند استخدام بنية Supabase Quick Start، يمكن أن يتضمن إعداد قاعدة البيانات جدولًا باسم `documents` ودالة بحث باسم `match_documents`، مع ضرورة مطابقة أسماء الجداول والدوال الفعلية مع إعدادات n8n.

## 6. استرجاع المعلومات وتوليد الإجابات (RAG AI Agent)

بعد تجهيز قاعدة المعرفة، يُبنى مسار آخر للتفاعل مع المستخدمين واسترجاع المعلومات.

### 6.1 استقبال السؤال

يُستخدم `Chat Trigger` لاستقبال سؤال المستخدم وتمريره إلى `AI Agent`.

### 6.2 معالجة السؤال

يستخدم `Google Gemini Chat Model` لفهم السؤال، وتحديد الحاجة إلى البحث في قاعدة المعرفة، وصياغة الإجابة النهائية.

النموذج اللغوي ليس قاعدة المعرفة نفسها؛ فالمعلومات الخارجية التي يعتمد عليها النظام تُخزّن في **Supabase Vector Store**.

### 6.3 البحث باستخدام Vector Store Tool

تُضبط `Supabase Vector Store` لتعمل كأداة يستطيع الـ Agent استخدامها لاسترجاع المستندات ذات الصلة.

يمكن إعطاء الأداة اسمًا واضحًا مثل:

`search_course_knowledge_base`

كما يجب أن يوضّح `Tool Description` أن وظيفتها البحث في قاعدة المعرفة لاسترجاع المعلومات المتعلقة بسؤال المستخدم.

يُستخدم نموذج Embeddings المتوافق مع مرحلة التخزين لتحويل السؤال إلى Vector، ثم تُجرى عملية **Similarity Search** لاسترجاع الأجزاء الأقرب إلى السؤال.

يمكن البدء بقيمة `Limit` مثل 4 نتائج، ثم تعديلها بناءً على نتائج الاختبار وجودة الاسترجاع.

### 6.4 توليد الإجابة (Generation)

بعد استرجاع الأجزاء ذات الصلة، يستخدم الـ Agent السؤال والمعلومات المسترجعة لصياغة الإجابة.

تعتمد موثوقية الإجابة على جودة المستندات، وملاءمة الأجزاء المسترجعة، وتعليمات النموذج. لذلك لا يعني نجاح عملية البحث بالضرورة أن الإجابة النهائية صحيحة بالكامل.

## 7. دور Memory مقارنةً بـ Knowledge Base

من المفاهيم الأساسية في المشروع التمييز بين **Memory** و**Knowledge Base**.

| العنصر | الوظيفة |
|---|---|
| **Simple Memory** | الاحتفاظ بسياق المحادثة ومعلومات الرسائل السابقة |
| **Supabase Vector Store** | تخزين المعرفة الخارجية واسترجاع المستندات ذات الصلة |

تساعد `Memory` على فهم الأسئلة اللاحقة التي تعتمد على سياق سابق، بينما يتيح **RAG** الوصول إلى المعلومات الموجودة في المستندات.

لا تُعد Memory بديلًا عن قاعدة المعرفة، كما أن وجود قاعدة المعرفة لا يعني تلقائيًا الاحتفاظ بسياق المحادثة.

## 8. تعليمات الـ Agent (System Instructions)

تحدد التعليمات دور المساعد وقواعد استخدام قاعدة المعرفة.

يتضمن التصميم تعليمات مثل:

- استخدام `search_course_knowledge_base` عندما يتطلب السؤال معلومات من قاعدة المعرفة.
- الاعتماد على المعلومات المسترجعة عند الإجابة عن الأسئلة المتعلقة بالمحتوى.
- عدم اختلاق معلومات لا تدعمها المصادر المسترجعة.
- توضيح عدم توفر معلومات كافية عندما لا تحتوي قاعدة المعرفة على إجابة مناسبة.
- عدم افتراض أن كل رسالة تحتاج إلى عملية بحث؛ بل اختيار الأداة وفق طبيعة الطلب.

تساعد هذه التعليمات على ضبط سلوك الـ Agent، لكنها لا تغني عن اختبار جودة الاسترجاع ومراجعة الإجابات الفعلية.

## 9. الاختبار والتحقق (Testing and Validation)

يجب اختبار مرحلتي تجهيز المعرفة واستخدامها بصورة منفصلة.

### 9.1 اختبار Knowledge Ingestion Pipeline

تشمل عملية التحقق:

- التأكد من استقبال الملف من Google Drive.
- التحقق من نجاح تنزيل الملف.
- التأكد من استخراج النص بصورة صحيحة.
- مراجعة تقسيم النص إلى Chunks.
- التحقق من إنشاء Embeddings.
- التأكد من تخزين السجلات في Supabase.
- مراجعة محتوى السجلات والـ Metadata.

### 9.2 اختبار RAG AI Agent

تشمل حالات الاختبار المقترحة:

| Test | الهدف |
|---|---|
| سؤال عن معلومة موجودة في المستند | التحقق من استرجاع المعلومات ذات الصلة |
| سؤال بصياغة مختلفة عن النص الأصلي | اختبار Semantic Retrieval |
| سؤال عن معلومة غير موجودة في قاعدة المعرفة | التحقق من عدم اختلاق إجابة |
| سؤال متابعة يعتمد على محادثة سابقة | اختبار Memory وسياق المحادثة |
| سؤال يحتاج إلى أكثر من مقطع | تقييم ملاءمة نتائج الاسترجاع وتكامل الإجابة |

يجب تسجيل نتائج الاختبارات الفعلية، ومراجعة المقاطع المسترجعة والإجابة الناتجة بدلًا من الاكتفاء بملاحظة أن الـ Workflow انتهى دون خطأ.

## 10. معالجة الأخطاء (Troubleshooting)

عند ظهور مشكلة، يمكن تحديد المرحلة التي تحتاج إلى المراجعة:

- **عدم ظهور سجلات في Supabase:** مراجعة Trigger وتنزيل الملف واستخراج النص وإعدادات Data Loader وEmbeddings.
- **فشل البحث في Vector Store:** التحقق من اسم الجدول ودالة البحث وإعدادات الاتصال.
- **عدم توافق الأبعاد:** التأكد من توافق نموذج Embeddings مع تعريف عمود Vector.
- **استرجاع نتائج غير مناسبة:** مراجعة جودة المستندات وChunk Size وChunk Overlap وLimit.
- **إجابات غير مدعومة بالمصادر:** مراجعة المقاطع المسترجعة وTool Description وSystem Instructions.
- **فشل الأسئلة اللاحقة:** مراجعة إعدادات Memory وربط الجلسة بالمحادثة الصحيحة.

يُفضّل تغيير إعداد واحد في كل مرة عند اختبار التحسينات، حتى يمكن تحديد أثره على النتائج.

## 11. الفرق بين Dify وn8n في بناء RAG

سبق أن تعرّفت على مفهوم RAG باستخدام Dify، بينما يهدف هذا المشروع إلى فهم تفاصيله من خلال بناء مكوناته وربطها باستخدام n8n.

| المفهوم | Dify | n8n |
|---|---|---|
| Knowledge Base | أدوات إدارة المعرفة في Dify | Supabase Vector Store |
| معالجة المستندات | وظائف مدمجة في المنصة | Workflow Nodes |
| Chunking | إعدادات معالجة المعرفة | Text Splitter |
| Embeddings | إعدادات النموذج | OpenAI Embeddings |
| Vector Storage | إدارة المعرفة داخل Dify | Supabase وpgvector |
| Retrieval | آليات الاسترجاع في Dify | Vector Store |
| AI Agent | تطبيق أو Agent داخل المنصة | AI Agent Node |
| Memory | سياق المحادثة بحسب الإعدادات | Simple Memory |

لا يعني ذلك أن إحدى المنصتين أفضل دائمًا من الأخرى؛ فالاختيار يعتمد على متطلبات المشروع ومستوى التحكم المطلوب في مكونات النظام.

## 12. حدود المشروع والتطوير المستقبلي

يركّز التصميم على تجهيز المستندات واسترجاع المعلومات منها وتوليد إجابات تعتمد على المحتوى المسترجع.

يمكن تطوير النظام مستقبلًا من خلال:

- تحسين ربط النتائج بمعلومات المصدر.
- إضافة ضوابط للخصوصية وإدارة صلاحيات الوصول.
- دمج RAG مع Workflows أخرى ضمن حلول **AI Automation**.

تُعد هذه التحسينات مقترحات مستقبلية ما لم تكن قد نُفذت واختُبرت بالفعل.

## 14. الخلاصة (Conclusion)

يوضح مشروع **RAG with n8n** كيفية بناء نظام يستقبل المستندات، ويعالج محتواها، ويحوّل أجزاءها إلى Embeddings، ثم يخزّنها في قاعدة بيانات متجهية لاستخدامها في استرجاع المعلومات.

كما يوضح كيفية ربط **Supabase Vector Store** بـ **AI Agent** لتمكينه من البحث في قاعدة المعرفة واستخدام النتائج في صياغة الإجابات.

تتمثل الفكرة الأساسية في فهم وظيفة كل مكوّن، وكيفية انتقال البيانات بين المراحل، وأهمية التحقق من جودة الاسترجاع قبل الاعتماد على الإجابة النهائية.
